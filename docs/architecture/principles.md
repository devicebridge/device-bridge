# Архитектурные принципы Device Bridge

## Назначение документа

Данный документ фиксирует основные архитектурные принципы проекта.

При разработке новых компонентов, проведении code review и принятии архитектурных решений предпочтение должно отдаваться решениям, соответствующим данным принципам.

Если реализация, обсуждение в issue или новый PR противоречат данным принципам, изменение должно быть предварительно оформлено отдельным ADR. До принятия ADR данный документ считается приоритетным источником архитектурных требований.

---

# 1. Одна ответственность

Каждый компонент отвечает только за одну задачу.

Компоненты не объединяют несколько независимых обязанностей.

---

# 2. Однонаправленные зависимости

Зависимости всегда направлены внутрь архитектуры.

Нижележащие компоненты не знают о вышележащих.

---

# 3. Связывание компонентов выполняет Runtime

Компоненты не взаимодействуют друг с другом напрямую.

Связь между компонентами организует Bridge Runtime.

---

# 4. Message — единый внутренний формат

Все внутренние компоненты обмениваются сообщениями типа Message.

Внутренние компоненты не зависят от транспортного протокола.

---

# 5. Сериализация выполняется только на границе системы

JSON и другие форматы используются только при взаимодействии с внешним миром.

Внутри проекта используются структуры Go.

---

# 6. Интерфейсы принадлежат потребителю

Интерфейс объявляется в пакете, который его использует.

Реализация не определяет собственные интерфейсы без необходимости.

---

# 7. Конфигурация является внешней

Компоненты не содержат встроенных настроек, зависящих от окружения.

Конфигурация передаётся извне.

---

# 8. Простота важнее преждевременной оптимизации

До версии 1.0 предпочтение отдаётся простым и понятным решениям.

Оптимизация выполняется только при наличии объективной необходимости.

---

# 9. Каждый PR должен быть законченным

Каждый Pull Request должен:

- решать одну задачу;
- оставлять проект в рабочем состоянии;
- сопровождаться тестами, если это применимо.

---

# 10. Документация является частью архитектуры

Архитектурные решения должны быть отражены в документации проекта.

Изменение архитектуры без обновления документации считается незавершённым изменением.
